# Native text-export overwrite audit

## Export contract

On macOS and Windows, the translation editor requests a save location through the locked `file_selector` package. If the user cancels, the draft is unchanged; after a location is returned, Kotoha passes only the chosen translation to the exporter as UTF-8 (`lib/main.dart`, `_exportTranslation`). The exporter stages the encoded bytes in a unique, operation-owned sibling directory and replaces the selected path only after the staged write completes. It does not read the old destination's contents. A failure before replacement leaves the previous bytes intact; an error after replacement may leave the new file in place. Cleanup removes only the operation-owned staged file and directory; it is not secure erasure.

The real-filesystem failure-injection test forces a partial staging write, then checks that the old destination bytes remain and staging is removed. A separate success test checks the exact UTF-8 bytes and cleanup. The platform CI logs below show both tests executing on macOS and Windows.

Apple's AppKit documentation says the Save panel asks whether to replace an existing file when the chosen name already exists. This supports a source-and-API-level confirmation path for the locked implementation, not an observation of a user's interaction. No test has selected an existing destination in the native dialog, pressed Cancel on its replacement alert, or confirmed replacement. Thus no native user interaction is claimed.

## Access-control preservation

Staging and replacement preserve the destination's measured access restrictions before plaintext is written or the final name is replaced. Required metadata-preservation failures abort without replacing the destination.

- **macOS:** for an existing destination, path-based `stat` and `acl_get_file(ACL_TYPE_EXTENDED)` inspect ownership, mode, and ACL without opening file data. `stat$INODE64` is used on x86_64 and plain `stat` on arm64. Before staging writes, inherited file ACL entries are removed individually with `acl_get_entry`, `acl_delete_entry`, and `acl_set_file` (whole-file `acl_delete_file_np` returned `ENOTSUP` on the hosted runner). The exporter opens a write-only stage handle, applies the destination owner/group/mode and ACL to the empty stage, then writes through that handle. When the destination has no extended ACL, inherited file ACL entries are removed; a new destination retains the selected parent directory's default ACL inheritance. The exact export test passed on macOS 26.7.2 arm64 and macOS 15.7.9 x86_64 in CI run `43827227683` (17 passed, 4 skipped on each architecture); the suite includes deny-read ACL staging/replacement, ACL-free replacement under an ACL-inheriting parent, parent-default ACL behavior, exact bytes, and partial-write preservation/cleanup. Logs: `vcs-read/b3e7cab8df424010990ca6eafebbecdd`, `vcs-read/a1d9323577b74eea8927a1c98d9de9c7`.
- **Windows:** for an existing destination, the exporter reads the DACL with `GetNamedSecurityInfoW` and applies it as a protected DACL to the empty stage before writing. It holds a write-only stage handle open so it need not reopen the path after applying restrictions. `ReplaceFileW` is used with flags `0`, without `IGNORE_ACL_ERRORS` or `IGNORE_MERGE_ERRORS`; errors propagate. New destinations use the selected directory's inherited ACL path and ordinary rename. The Windows debug-build check on Windows Server 2025 passed in run `43827227683`; its export test reported 14 passed and 7 skipped, including protected-DACL preservation, parent-default DACL behavior, exact output, and partial-write preservation/cleanup. Log: `vcs-read/3c4ec75d80b947638dd0f0f90977f962`.
- **Linux host tests:** the POSIX path uses a private staging directory and preserves owner/group/mode plus the exact access ACL for an existing destination; new staged files retain the selected parent directory's default ACL. The post-create `chmod(0700)` prevents inherited default ACL entries from making staged plaintext accessible to other users. The current Flutter CI test job passed. Kotoha currently has no Linux desktop export action; these tests exercise host filesystem behavior and do not establish a supported Linux export feature.

These tests do not promise timestamps, file flags, extended attributes, resource forks, hard-link identity, creation-time semantics, power-loss durability, behavior on every filesystem/filter driver, or safety against concurrent external replacement of the destination path. No crash-durability or path-race guarantee is made.

## Native UI test boundary

The native macOS panel UI test is intended to establish accessibility, cancellation, and preservation of the in-memory draft; it does not exercise overwrite confirmation. In CI run `43827227683` on SHA `186136ba3592e57b08a7af1c59c51350759b6e3c`, the macOS debug/accessibility check failed at `NativeExportPanelUITests.swift:114` before field entry or panel presentation. Its diagnostic reports `voiceOverEnabled=true`, `axClientTrusted=false`, enhanced-UI status `-25211`/unavailable, zero scroll views, and missing target/source-language/source-text nodes while the app window is present (`vcs-read/360e43ef5862429ea7746bcaa39ee09f`). This establishes failure of that hosted accessibility-query path only; it does not diagnose user-run macOS behavior or establish the native save panel's behavior.

The current publication's export-specific macOS arm64, macOS x86_64, Windows, and Flutter-test checks passed. The overall workflow was not wholly green: the separate macOS accessibility, Android instrumentation, and Linux portal checks failed. Preserve the native test assertions and do not describe these results as a complete product release gate.
