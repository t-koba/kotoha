# Native text-export overwrite audit

## Export contract

On macOS and Windows, the translation editor requests a save location through the locked `file_selector` package. If the user cancels, the draft is unchanged; after a location is returned, Kotoha passes the content to the exporter as UTF-8: either only the chosen translation (`lib/main.dart`, `_exportTranslation`) or one reversible plain-text document holding the source and all translations (`_exportWorkspace`, formatted by `lib/workspace_export.dart`); the same format can be read back by the Restore action. The exporter stages the encoded bytes in a unique, operation-owned sibling directory and replaces the selected path only after the staged write completes. It does not read the old destination's contents. A failure before replacement leaves the previous bytes intact; an error after replacement may leave the new file in place. Cleanup removes only the operation-owned staged file and directory; it is not secure erasure.

The real-filesystem failure-injection test forces a partial staging write, then checks that the old destination bytes remain and staging is removed. A separate success test checks the exact UTF-8 bytes and cleanup. The platform CI results below show both tests executing on macOS and Windows.

## Reversible v2 format and restore

The earlier v1 workspace export was a presentation format, not a reversible serialization: verbatim bodies could contain the format's own header lines, so two different drafts serialized to byte-identical output (experiment `8e73a3c20fb6463ebf482443b263b78b`). A parser could not recover the original field boundaries without risking silent corruption. v1 is no longer produced.

The current document begins with `Kotoha workspace export v2` and holds one escaped line per field. Language labels and text bodies all escape backslash, carriage return and line feed, so no field can contain an unescaped newline or imitate a structural line. `lib/workspace_export.dart` owns both `formatWorkspaceExport` and `parseWorkspaceExport`; exports always use LF endings. The parser accepts LF or CRLF structural line endings (a Windows text editor can re-save a `.txt` with CRLF), normalizes CRLF to LF before field checks, and rejects a remaining raw carriage return, an unknown version, a missing final newline, an unexpected field, an incomplete translation pair or an unknown escape with a `FormatException` instead of guessing boundaries. A body containing header-like text therefore stays in its own field. Restore accepts at most 8 MiB, so export preflights the encoded v2 bytes against that cap. Above the cap, a warning discloses that the file cannot be restored before the save panel opens; the user can still save the UTF-8 text, and the success notice distinguishes that non-restorable file from a normal reversible export.

Restore uses the existing text-document picker on every platform. When the current workspace holds any text, a confirmation dialog precedes replacement of the source language, source text and all translation fields. Picker cancellation leaves the workspace unchanged without a notice, matching text import; a wrong file type, an unsupported format, an oversized document or a read failure leaves it unchanged and reports its own notice. On mobile the native adapters reject wrong types and oversized documents before returning bytes, and surface `unsupported_type` / `too_large` channel codes that restore maps to those notices; text import stays fail-closed with its generic notice. An edit detected after picking, including a language-only edit, also aborts the restore and keeps those edits. Restore replaces only in-memory session state; it adds no persistence, dependency or model path.

## Native overwrite consent

The lock pins `file_selector_windows` 0.9.3+6 (archive SHA-256 `fbefc5fb92c6d3cbe8d284a2cd971b593bb07d2cd6da8557b81a862250b4acec`) and `file_selector_macos` 0.9.5+2 (archive SHA-256 `d785431f1910aac8a50e5c492cae912320158030a88703c67b9ef7f1f96fd7ba`). Pub metadata reports those same archive hashes. Their upstream tags resolve to Windows commit `9854cd5607da4001f2dd3cbdcd6903202d28958c` and macOS commit `f2c6798b45a7ae936feb6798fe45cb51f832dc18`; each tag's `pubspec.yaml` declares the locked version. Inspected source hashes: Windows plugin `17e0345a6c0a508986d7d2100ecd04880339b40459c46bb1c14370cbce4b2d3e`, Windows option controller `b35502bb981c2e19b201c2c0bd7202dc25d0b255ac5fef66fec4b80da63e4d4e`, and macOS Swift plugin `2ce6820e865f645c7823c82091d1df2a3a2f36662add35fd75d509b9a5bcc24d`. The locked archive bytes were not independently compared with extracted tag contents, so archive-to-tag byte identity remains unverified.

- **Windows:** the pinned plugin selects its save-dialog mode, which creates `CLSID_FileSaveDialog`. Kotoha's save request does not request folder or multiple selection. When plugin options are added, the implementation ORs them into the dialog's existing flags and forwards the flags to `IFileDialog::SetOptions`; it does not clear `FOS_OVERWRITEPROMPT`. Microsoft documents `FOS_OVERWRITEPROMPT` as the default for the Common Item Dialog's Save mode and as prompting before replacement of an existing same-name file. The inspected path therefore retains the documented native prompt. Sources: [pinned plugin](https://github.com/flutter/packages/blob/9854cd5607da4001f2dd3cbdcd6903202d28958c/packages/file_selector/file_selector_windows/windows/file_selector_plugin.cpp), [pinned controller](https://github.com/flutter/packages/blob/9854cd5607da4001f2dd3cbdcd6903202d28958c/packages/file_selector/file_selector_windows/windows/file_dialog_controller.cpp), [Microsoft Common Item Dialog](https://learn.microsoft.com/en-us/windows/win32/shell/common-file-dialog), [`FILEOPENDIALOGOPTIONS`](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/ne-shobjidl_core-_fileopendialogoptions).
- **macOS:** the pinned plugin creates an `NSSavePanel` and presents it through the standard sheet/modal APIs; it sets no overwrite-related option and installs no delegate that suppresses the panel's replacement behavior. Apple's AppKit documentation says the Save panel asks whether to replace an existing file when the chosen name already exists. This supports a source-and-API-level confirmation path for the locked implementation, not an observation of a user's interaction. Source: [pinned plugin](https://github.com/flutter/packages/blob/f2c6798b45a7ae936feb6798fe45cb51f832dc18/packages/file_selector/file_selector_macos/macos/file_selector_macos/Sources/file_selector_macos/FileSelectorPlugin.swift); [Apple AppKit documentation](https://developer.apple.com/documentation/appkit/nsopensavepaneldelegate/panel(_:userenteredfilename:confirmed:)).

The exporter does not show a second prompt or change the chooser's options; it begins only after the chooser returns a path. No test has selected an existing destination in the native dialog, pressed Cancel on its replacement alert, or confirmed replacement. Thus no native user interaction is claimed.

## Access-control preservation

Staging and replacement preserve the destination's measured access restrictions before plaintext is written or the final name is replaced. Required metadata-preservation failures abort without replacing the destination.

- **macOS:** for an existing destination, path-based `stat` and `acl_get_file(ACL_TYPE_EXTENDED)` inspect ownership, mode, and ACL without opening file data. `stat$INODE64` is used on x86_64 and plain `stat` on arm64. Before staging writes, inherited file ACL entries are removed individually with `acl_get_entry`, `acl_delete_entry`, and `acl_set_file` (whole-file `acl_delete_file_np` returned `ENOTSUP` on the hosted runner). The exporter opens a write-only stage handle, applies the destination owner/group/mode and ACL to the empty stage, then writes through that handle. When the destination has no extended ACL, inherited file ACL entries are removed; a new destination retains the selected parent directory's default ACL inheritance. The exact export test passed on macOS 26.7.2 arm64 and macOS 15.7.9 x86_64 in CI on SHA `186136ba3592e57b08a7af1c59c51350759b6e3c` (17 passed, 4 skipped on each architecture); the suite includes deny-read ACL staging/replacement, ACL-free replacement under an ACL-inheriting parent, parent-default ACL behavior, exact bytes, and partial-write preservation/cleanup.
- **Windows:** for an existing destination, the exporter reads the DACL with `GetNamedSecurityInfoW` and applies it as a protected DACL to the empty stage before writing. It holds a write-only stage handle open so it need not reopen the path after applying restrictions. `ReplaceFileW` is used with flags `0`, without `IGNORE_ACL_ERRORS` or `IGNORE_MERGE_ERRORS`; errors propagate. New destinations use the selected directory's inherited ACL path and ordinary rename. The Windows debug-build check on Windows Server 2025 passed on SHA `186136ba3592e57b08a7af1c59c51350759b6e3c`; its export test reported 14 passed and 7 skipped, including protected-DACL preservation, parent-default DACL behavior, exact output, and partial-write preservation/cleanup.
- **Linux host tests:** the POSIX path uses a private staging directory and preserves owner/group/mode plus the exact access ACL for an existing destination; new staged files retain the selected parent directory's default ACL. The post-create `chmod(0700)` prevents inherited default ACL entries from making staged plaintext accessible to other users. The current Flutter CI test job passed. Kotoha currently has no Linux desktop export action; these tests exercise host filesystem behavior and do not establish a supported Linux export feature.

These tests do not promise timestamps, file flags, extended attributes, resource forks, hard-link identity, creation-time semantics, power-loss durability, behavior on every filesystem/filter driver, or safety against concurrent external replacement of the destination path. No crash-durability or path-race guarantee is made.

## Native UI test boundary

The native macOS panel UI test is intended to establish accessibility, cancellation, and preservation of the in-memory draft; it does not exercise overwrite confirmation. In CI on SHA `186136ba3592e57b08a7af1c59c51350759b6e3c`, the macOS debug/accessibility check failed at `NativeExportPanelUITests.swift:114` before field entry or panel presentation. Its diagnostic reports `voiceOverEnabled=true`, `axClientTrusted=false`, enhanced-UI status `-25211`/unavailable, zero scroll views, and missing target/source-language/source-text nodes while the app window is present. This establishes failure of that hosted accessibility-query path only; it does not diagnose user-run macOS behavior or establish the native save panel's behavior.

On SHA `e681faf32f1fd8b2ed9c98c59adcb6977b65ccfa`, CI passed the export-specific macOS arm64 and x86_64, Windows, Flutter-test, Android instrumentation (22 tests), and iOS simulator checks. The overall workflow was not wholly green: the separate macOS accessibility check failed again because the hosted runner's Accessibility API is disabled for the XCUI client (`axClientTrusted=false`, `-25211`/kAXErrorAPIDisabled, empty accessibility tree), and the Linux portal probe failed. The native test assertions remain; these results are not a complete product release gate.

The runner-side cause is now established from the operator's authoritative answer and the public runner-image provisioning script. The operator manages nothing on hosted runners and cannot grant macOS permissions there; the public macOS image pre-populates the Accessibility TCC database during image build (`images/macos/scripts/build/configure-tccdb-macos.sh`) for specific clients such as `/bin/bash`, `/usr/bin/osascript`, `com.apple.dt.Xcode-Helper` and the runner provisioner, but not for the XCUI test runner. Xcode builds a separate `*-UITests-Runner.app`; macOS evaluates Accessibility trust for that runner process, which reads the target's accessibility tree over AXUIElement. With that client untrusted (`AXIsProcessTrusted() == false`, `kAXErrorAPIDisabled`/`-25211`), XCUI queries return an empty tree, matching the exact CI diagnostic (six native buttons but no text fields, text views, scroll views or target nodes). On macOS 13 and later `tccutil` can reset a TCC entry but cannot grant one; a grant needs either a pre-provisioned custom runner image or a developer-signed helper, both outside this project's hosted-runner workflow and requiring operator-owned infrastructure and signing. No scroll/query change or alternative app-side semantic exposure can grant an untrusted client access, so no assertion was weakened and no dependency was adopted on this basis. Until a trusted Accessibility grant is provisioned for the test runner, this check remains an unmet hosted-runner environment limitation and not evidence about user-run macOS behavior or the native panel.

Current CI state: `NativeExportPanelUITests` is kept in the sources but is no longer a `CI` job step, so the native save panel's accessibility, cancellation and in-memory draft preservation are no longer checked by CI. The Flutter `text_export_test.dart` cancellation and draft-preservation assertions still run on hosted runners; they do not exercise the native panel. Observing the removed path requires a runner whose XCUI client has Accessibility trust.
