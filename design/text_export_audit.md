# Native text-export overwrite audit

Kotoha's desktop text export asks the locked `file_selector` implementation for a save path and then writes the selected translation with `File(path).writeAsBytes`. The write replaces/truncates a file at that path; overwrite safety therefore depends on the native save panel obtaining consent before returning it.

## Locked implementations

`pubspec.lock` pins `file_selector_windows` 0.9.3+6 (archive SHA-256 `fbefc5fb92c6d3cbe8d284a2cd971b593bb07d2cd6da8557b81a862250b4acec`) and `file_selector_macos` 0.9.5+2 (archive SHA-256 `d785431f1910aac8a50e5c492cae912320158030a88703c67b9ef7f1f96fd7ba`). These are also the direct constraints in `pubspec.yaml`. The corresponding upstream package tags resolve to commits `9854cd5607da4001f2dd3cbdcd6903202d28958c` (Windows) and `f2c6798b45a7ae936feb6798fe45cb51f832dc18` (macOS). The inspected Windows plugin source SHA-256 is `17e0345a6c0a508986d7d2100ecd04880339b40459c46bb1c14370cbce4b2d3e`; the macOS Swift plugin source SHA-256 is `2ce6820e865f645c7823c82091d1df2a3a2f36662add35fd75d509b9a5bcc24d`.

- **Windows: overwrite consent is specified by the platform default.** In the pinned Windows source, `ShowSaveDialog` selects save mode, which creates `CLSID_FileSaveDialog`; the wrapper does not call `SetOptions` for the normal save path or remove any option. Microsoft documents `FOS_OVERWRITEPROMPT` as prompting before overwriting an existing same-name file and as a *default value for the Save dialog*. The wrapper's only optional flags here are for folder or multiple selection, neither used by Kotoha's save request. Thus the exact implementation retains the Windows save-dialog overwrite prompt. Sources: [pinned Windows implementation](https://github.com/flutter/packages/blob/file_selector_windows-v0.9.3%2B6/packages/file_selector/file_selector_windows/windows/file_selector_plugin.cpp), [Microsoft FILEOPENDIALOGOPTIONS](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/ne-shobjidl_core-_fileopendialogoptions).
- **macOS: default native panel is used, but the retrieved contract is not enough to claim the prompt is guaranteed.** The pinned Swift plugin creates `NSSavePanel()`, configures directory/name/button/type/directory-creation fields, and displays it as a sheet or modal panel. It does not set any overwrite-related property or install a delegate. Apple's current AppKit JSON reference describes `NSSavePanel` as a location-selection panel and `savePanel()` as initializing default information; its overview and indexed public properties do not specify an overwrite-confirmation guarantee. The exact JSON fetch is receipt `cebfbfe734643b6ccd14350b586d46d8729462dc18be7f37ab0156f87e233cb2`, SHA-256 `e0c7e6ce0d9bd7a56c972c8e9dfcd859a9a19958cfea911c624e213ba9c2ba41`. The archived file-system guide also recommends this standard panel for export but does not settle the exact behavior. Sources: [pinned macOS implementation](https://github.com/flutter/packages/blob/file_selector_macos-v0.9.5%2B2/packages/file_selector/file_selector_macos/macos/file_selector_macos/Sources/file_selector_macos/FileSelectorPlugin.swift), [Apple NSSavePanel](https://developer.apple.com/documentation/appkit/nssavepanel.md), [Apple save-panel guide](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/FileSystemProgrammingGuide/UsingtheOpenandSavePanels/UsingtheOpenandSavePanels.html).

## What the app tests establish

`test/text_export_test.dart` checks exact UTF-8 output, selected-translation-only writing, the mocked save request, cancellation, and write-error behavior. It replaces `FileSelectorPlatform.instance` with a fake, so it does **not** show the Windows or macOS native UI and cannot test overwrite confirmation. The Apple CI job in `.github/workflows/ci.yml` runs the iOS simulator `RunnerTests` and accessibility UI tests, then builds macOS; it does not run the macOS `RunnerTests` target or automate an `NSSavePanel`. `macos/RunnerTests/RunnerTests.swift` currently contains only the generated placeholder test. No direct native existing-file replace/cancel observation is recorded here. Do not interpret these tests or the macOS build as native-dialog coverage.

No export code was changed in this audit: the Windows platform contract explicitly prompts before replacement; the exact macOS implementation delegates to its system panel, but the source and documentation inspected here leave the overwrite guarantee unresolved. To close the remaining macOS question, exercise the pinned panel on a macOS runtime against an existing file, verify that cancelling the replacement prompt leaves the bytes untouched and accepting it returns the selected path, or add a documented application-level confirmation if the runtime does not provide that guarantee. Keep the selected-translation-only and cancellation contracts intact.
