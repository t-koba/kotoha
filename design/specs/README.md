# ことは データ・処理契約

本文の能力ベースの設計を、機械可読の構造と宣言へ対応させる。

## 構造と意味の検査

JSON Schemaはフィールドと型を扱う。ファイルの参照、許諾の対象、言語経路、グラフの接続、イベントの順序は意味検査で確認する。例示データは検査用の合成情報である。

| 契約 | 構造検査の後に行う確認 |
|---|---|
| モデル | ファイル集合・容量・許諾本文・許諾対象・言語経路・必要能力 |
| モード | 登録済み操作・パラメーター・型・権限・接続・到達可能性・循環 |
| イベント | ジョブと実行ID・順序・冪等な再送・終端・進捗整合 |
| 依存方針 | 採用する許諾条項の組み合わせ、配布区分、根拠と通知 |
| 保存 | 外部キー、親子関係、資料と参加者の所属、スナップショット参照 |
| C ABI | 型、所有権、呼出し順序、資源予算、契約照会 |

スキーマの`$schema`は使用する外部標準を示す。契約の適合は必要能力と構造の一致で確認する。

## モデルの検査

署名付きカタログと持込みファイルは、由来を別に記録する。署名の検証では署名対象の原バイト列を使用し、その後にJSONを解析する。モデル資産は整合性、形式、演算、資源を検査する。

言語タグの正規化と登録情報の照合は言語アダプターが担当する。付属検査はフィールドの構文と参照整合を扱う。個別言語の翻訳品質は評価プロファイルで測定する。

## モードの実行

操作レジストリには各操作の入力・出力型、必須能力、必要権限、パラメーター契約を登録する。モードはそのレジストリへ解決する。新しい処理実装は配布工程、処理の組み合わせはモード定義として管理する。

ノードはsource、processor、sinkの役割を持つ。入力ポートは宣言された型と接続数へ適合し、全ノードが入力から出力へ至る経路に属する。反復実行とストリームの継続はジョブ管理が担当する。

## イベントと保存

イベントは`job_id`、`run_id`、`sequence`、`kind`、`payload`で識別する。部分結果、確定結果、訂正結果を区別する。`input_snapshot`は保存側の`segment_snapshots.snapshot_id`に対応し、現在の処理対象との一致を実行時に確認する。

同一イベントの再送は冪等に適用し、同じ順序位置に異なる内容が到着した場合は整合性エラーとして扱う。終端イベントを確定し、確定結果を安全に受け渡してから資源を解放する。保留キューは設定した予算でバックプレッシャーをかける。

SQLは暗号化ストレージに適用する論理構造を定義する。親ジョブ参照は系譜情報であり、親の削除時には残る子ジョブの参照をNULLにする。別プロジェクトの子ジョブは連鎖削除しない。付属検査はSQLiteによる構文と参照の検査であり、暗号化・鍵管理・実行時の権限はストレージ実装の試験対象とする。

## C ABI

各構造体の`struct_size`と必要能力を確認して呼び出す。入力の借用は呼出し中、非同期入力はエンジンが所有するコピーとして扱う。出力は呼出元のバッファへ格納する。容量不足時は必要なバイト数を返し、イベントを受信待ちに保持する。

同一エンジンへの呼出しは所有キューで順序付けする。取消はハンドルの有効期間中に行い、終端とキュー排出を確認して解放する。解放と呼出しは所有者が同期する。

## 検査の実行

Pythonと`jsonschema`を使用する。ヘッダーの読込み検査にはCとC++のコンパイラーを使用する。

```sh
python -m pip install jsonschema
python specs/validate_specs.py
```

検査スクリプトはモデル・音声・文書の推論処理を行うアプリ実装から独立した、契約の検査用ツールである。
