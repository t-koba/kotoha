# ことは 設計書

**kotoha／ことは**  
あらゆる翻訳を、手元で。

ことはは、文字・資料・画像・音声・映像を利用者の端末で扱う、多言語の翻訳環境である。個人で読む・調べる・書く・聞く作業と、人と伝え合う作業を、共通の入力、処理、編集、出力の仕組みで支える。

対象プラットフォームはWindows、macOS、Linux、iOS、iPadOS、Androidとする。本書は製品要求、構造、処理契約、保存、配布、検証を定義する。性能値を設定する際は測定条件と受入基準を組にし、測定結果と設計目標を区別する。

## 設計原則

| 原則 | 仕様への反映 |
|---|---|
| 利用者の目的を中心にする | 入力形式、表示、保存、出力を組み合わせて作業環境を作る |
| 多言語を対等に扱う | 対応範囲を処理能力から導き、言語・文字体系・地域表記を個別に管理する |
| 処理を手元で制御する | 認識・翻訳・合成・解析は利用端末で実行する |
| 資源を必要な分だけ使う | 機能の初期化、モデルの保持、計算、入出力を用途に応じて調整する |
| 選択の余地を保つ | モデル、エンジン、処理方式、UI、プラットフォームを独立した契約で接続する |
| 権利と責任の境界を明確にする | アプリの配布資産、利用者が導入するモデル、外部OS機能を分けて管理する |
| 入力と成果を追跡できるようにする | 元資料、編集、生成条件、結果、位置、時間、話者を関連付ける |
| 不確実な結果を扱えるようにする | 認識途中、確定、要確認、人による修正を区別し、訂正と再処理を支える |
| 安全性を構造で支える | 所有権、入力範囲、資源予算、実行権限、復旧点を契約として定義する |
| 利用可能性を説明する | 各機能の成立条件、必要な導入物、品質の根拠、実行方法を表示する |

## 1. 製品の範囲

### 1.1 作業の基本形

作業は「取り込む → 理解するための処理 → 確認・編集 → 利用する」で構成する。入力と出力は複数を許容する。文章を複数言語へ翻訳する、資料を対照表示しながら読み上げる、映像に字幕を付ける、といった組み合わせを同じ基盤で扱う。

モードは、この組み合わせに表示方法と資源方針を添えたプリセットとする。利用者はプリセットを選び、必要な入力先、訳先、表示、保存を調整できる。利用頻度に応じたピン留め、並べ替え、作業設定の保存を提供する。

## 2. 多言語と参加者のモデル

### 2.1 言語を扱う単位

UIの表示言語、入力の言語、区間ごとの推定言語、出力先の言語、参加者が読みたい言語、読み上げ音声の言語をそれぞれ保持する。言語タグはBCP 47を使用し、文字体系、地域、必要な拡張を保持する。[S01]

一つの資料や発話に含まれる複数言語は、資料全体と区間の両方へ記録する。言語推定結果には候補と根拠を添え、利用者が指定・訂正できる。処理に十分な根拠が揃うまで、未確定として扱う。

### 2.2 言語ごとの能力

能力情報は「どの処理を、どの入出力条件で実行できるか」を表す。翻訳は方向付きの言語経路、OCRは言語・文字体系・縦横配置、音声認識は言語と音響条件、音声合成は言語・音声・出力形式で登録する。複合モデルには、音声から訳文などの直接経路も登録できる。

対応判定は経路の存在と必要条件で行う。入力言語一覧と出力言語一覧の組み合わせは、提供元が保証する方向の情報と合わせて解釈する。表示は「提供元の申告」「評価で確認した条件」「利用者が試す構成」を分ける。

同じ機能に複数の適合経路がある場合は、品質、遅延、メモリ、電力、利用条件、利用者の優先順位で選ぶ。経由言語を使う構成は経路として提示する。

### 2.3 UIと文字処理

UI文言はメッセージキーとローカライズ資産で管理する。導入済みのUI言語から利用者が選択でき、欠ける文言の表示先も設定で決める。翻訳対象言語の追加とUI文言の追加は独立させる。

Unicodeの書記素、結合文字、双方向表示、縦書き、文字幅、改行、音写を扱う。原資料の文字列と検索・比較用の正規化表現を分ける。フォントの選択は文字範囲と利用許諾で決める。

### 2.4 参加者と表示先

参加者はID、表示名、希望する読解言語の集合、表示領域、向き、声の照合設定、同意状態を持つ。話者、席、言語、表示先を独立した関係として管理する。

参加者数と表示領域数は画面・操作性・処理能力から決める。対面配置、円卓配置、一覧、個別フォーカスを同じ参加者データで表す。各発話は必要な訳先の集合へ配信し、同じ訳先と生成条件の結果を共有する。

## 3. UXと作業空間

入口は「翻訳」「取り込む」「会話」「ライブラリ」を基本にする。取り込み対象と利用目的から必要な処理を提案する。利用者の頻用操作をホームに配置できる。

コンパクトな画面は上下・切替表示、広い画面はサイドバーと複数ペインへ適応する。ウィンドウ幅、入力方式、表示倍率、利用中のモードからレイアウトを決定する。

| 画面 | 表示と操作 |
|---|---|
| 翻訳作業 | 原文、訳文、言語、処理構成、文体・用語、停止、確認・編集 |
| 資料リーダー | 目次、ページ・区間、原文との対応、進捗、検索、出力 |
| 視覚翻訳 | 対象領域、原文、訳文、フリーズ、領域修正、表示方式 |
| 字幕 | 入力元、認識・翻訳状態、時間、話者、遅延、固定・追従 |
| 対面 | 読む方向に合わせた表示、参加者設定、発話指定、訂正 |
| モデル管理 | 能力、入出力言語、導入条件、容量、提供元、利用許諾 |
| ジョブ | 進捗、待機理由、資源予算、再開点、取消、成果物 |
| ライブラリ | 資料、対訳、用語、保存期間、検索、バックアップ |
| 設定 | 表示、言語、保存、権限、電力、通信、ライセンス、診断 |

結果は認識途中、翻訳途中、確定、利用者による編集、要確認に区別する。表示更新は安定した部分を保ち、修正された区間を追跡可能にする。操作開始と状態変化を視覚・音声・触覚の適切な組み合わせで通知する。

アクセシビリティは共通の受入項目とする。読み上げの通知頻度、フォーカスの維持、文字拡大、色以外の状態表現、キーボード操作、代替入力を全画面で検査する。

## 4. システム構造

```text
共通UI・作業設定                     CLI・OS連携
          │                              │
          └──────── アプリケーション層 ────┘
                   作業・言語・同意・ジョブ
                   能力解決・資源・保存
                              │
                     型付き処理契約
                     ／          ＼
                C ABI / FFI    ローカルIPC
                     ＼          ／
                 処理エンジンとアダプター
                 翻訳・認識・合成・解析

OSアダプター：表示・入力・音声・カメラ・ファイル・鍵・電力・権限
```

### 4.1 実装上の責務

| 部品 | 責務 | 接続する契約 |
|---|---|---|
| Workspace | 操作、表示、編集、確認 | セグメント、ジョブ、表示設定 |
| CapabilityResolver | 実行可能な処理経路の探索 | エンジン・モデル・OSの能力 |
| JobCoordinator | 状態、期限、優先度、再開点 | 実行計画とイベント |
| ResourceScheduler | CPU・GPU・メモリ・電力の配分 | 資源見積りと測定値 |
| ModelRegistry | 導入物、内容、能力、状態 | モデルマニフェスト |
| ConsentStore | 許諾、目的、範囲、撤回 | 同意記録と根拠 |
| AcquisitionBroker | 許可された取得・転送 | 目的・接続先・期限付き許可 |
| EngineBroker | ローカル実行の接続と障害処理 | C ABIまたは認証付きIPC |
| ModelAdapter | モデル固有の入出力と処理条件 | 型付き入出力と能力記述 |
| ArtifactStore | 元資料、編集、検索、出力 | 暗号化保存と保持方針 |
| PlatformAdapter | OS能力と権限の公開 | 公開OS APIと許可されたハンドル |

アプリケーション層は純Dartを基本にし、UIとOS接続から独立させる。ネイティブの計算と既存ライブラリへの接続にはC++を使い、所有権の境界をC ABIへまとめる。プラットフォーム固有コードは適した言語で実装し、共通契約へ接続する。

## 5. UI基盤とLinux統合

### 5.1 共通UI

Flutterを共通の表示・操作基盤とする。フレームワークはBSD系の許諾で公開され、エンジンとOS埋込み層を分ける構造を持つ。[S02][S03] 採用対象は実際の配布物と推移的依存まで確認して確定する。

Android、iOS、iPadOS、Windows、macOSは、対応するFlutterの埋込み層と自前のOSアダプターを接続する。共通処理はバックグラウンドの実行キューへ割り当て、UIは状態と結果を受け取る。

### 5.2 Linuxホスト

Flutterの標準Linux構成はGTKを利用し、GTKはLGPLの許諾条件を持つ。[S04][S05] ここを配布方針に整合させるため、Linuxは**Flutter Engineの公開埋込みAPIと許諾型のホスト部品を組み合わせる構成**とする。埋込みAPIは、ウィンドウツールキットから独立した接続点として公開されている。[S06]

ホストの窓・描画面・入力にはSDLを採用候補とし、アクセシビリティの橋渡しにはAccessKitを評価する。SDLはzlib、AccessKitはMITまたはApacheの許諾で公開されている。[S07][S08] 組込み対象は選択した機能と依存の閉包で決める。

SDLのLinux向け機能には、利用可能なライブラリを実行時にロードする経路がある。[S09] ビルド設定、プラグイン探索、実行時ロードを配布監査へ含める。選択したLinux接続はWayland／X11、入力メソッド、クリップボード、画面倍率、アクセシビリティ、ファイル選択、音声、画面取得を担当する。OSサービスへの接続は監査済みクライアントまたは公開プロトコルを用いる。

このホストは製品側の実装・保守対象になる。文字入力、候補表示、ドラッグ＆ドロップ、複数画面、フォーカス、画面読み上げ、デスクトップ統合を基盤工程の受入項目とし、共通UIの利点と保守費用を同じ評価表で管理する。

### 5.3 軽量性の評価

UIの選定は配布容量、起動時間、常駐メモリ、表示負荷、操作性、OS統合、保守範囲の総合評価で行う。推論部分はUI契約から独立しているため、表示基盤の改善を局所的に適用できる。

## 6. エンジン、モデル、能力

### 6.1 三つの管理単位

| 単位 | 含むもの | 管理主体 |
|---|---|---|
| 実行エンジン | 演算実装、アクセラレーター接続、資源管理 | アプリの配布・検査工程 |
| アダプター | 入力構築、前後処理、停止条件、言語コード対応 | アプリの配布・検査工程 |
| モデル資産 | 重み、語彙、モデル付属データ、音声・文字認識資産 | 利用者の導入・許諾操作 |

エンジン候補にはllama.cpp、whisper.cpp、ONNX Runtime等を含む。これらは処理能力の提供者として接続し、用途に必要な実装だけを配布構成へ含める。[S10][S11][S12]

モデル候補はカタログ情報として扱う。特定モデルの形式、言語数、計算量を製品全体の条件へ広げず、アダプターと能力情報へ収める。PLaMoも対応を評価するモデル群の一つとして登録できる。

### 6.2 能力の解決

実行計画は、処理要求、導入モデル、エンジン実装、OS機能、利用条件、許可、資源予算を照合して作成する。各候補には成立する条件と評価根拠を添える。

推論経路は、文字認識から翻訳、音声認識から翻訳・合成、複合モデルによる直接処理などを同じ入出力型で比較する。利用者が求める原文確認、時刻、領域、話者情報も経路選択の条件に含める。

### 6.3 バックエンド

CPU、GPU、その他の演算装置はエンジンごとの実装済み能力として登録する。選択は演算適合、結果の一致、ピークメモリ、継続負荷、遅延、エネルギーの測定で決める。構成と環境の変化に応じて評価結果を再確認する。

## 7. モデル導入と利用許諾

### 7.1 配布の境界

アプリの配布物は、実行コード、UI資産、説明、接続定義、必要なライセンス通知で構成する。**推論用のモデル資産は、用途と容量にかかわらず利用者が別途導入する。** 翻訳、OCR、音声認識、発話検出、話者処理、音声合成、追加学習用データ、モデル固有の語彙・辞書も同じ導入管理へ置く。

モデル導入前でも、設定、モデル選択、資料整理、保存済み対訳の閲覧、手動編集を利用できる。既にOS側へ導入された機能は、提供条件とローカル実行の根拠を確認した能力として接続できる。

### 7.2 導入フロー

```text
用途・モデルの選択
  → 能力・必要資源・提供元の表示
  → 許諾本文・用途条件・表示義務の確認
  → 同意と必要な利用資格の確認
  → 提供元から取得／手元のファイルを取込み
  → 内容・署名・形式・依存・演算・資源を検査
  → 試験ロード
  → 管理領域へ登録
```

許諾本文とマニフェストをファイルで取り込めるようにする。同意記録は、対象、本文の内容識別、用途、当事者、日時、必要な追加手続の根拠を持つ。

### 7.3 マニフェスト

`model_manifest.schema.json`は、モデルID、表示名、提供元、ファイル一覧、内容ハッシュ、サイズ、用途、エンジン能力、アダプター、言語経路、資源条件、許諾情報を定義する。カタログの信頼性、モデル形式の適合性、推論品質の評価はそれぞれ記録する。

検査では署名対象の原バイト列を固定し、署名、長さ、ファイルハッシュ、パス、形式、メタデータ、演算を順に確認する。内容ハッシュは同一性の証拠として扱い、実行の安全性はパーサーの検査と資源制御で支える。

マニフェストはデータとして解釈する。実行可能な処理はアプリが提供する登録済みの実装へ解決する。

### 7.4 利用者と提供者の責務

モデルの別導入によって配布資産と利用者の選択を分離する。モデル利用時には当該モデルの条件を適用し、アプリ提供者の開発・試験・提供形態についても該当条件を確認する。たとえばPLaMoの許諾には用途・再配布・表示等の条件がある。[S13]

カタログには利用条件の読みやすい要約と原文を併記する。権利処理の単純さはモデル選択の評価項目に含める。モデルや許諾の変更時には、影響する利用条件を提示し、必要な確認を得る。

### 7.5 保持と切替

モデルは検査済みの不変な内容として管理し、ジョブが使用する内容を固定する。切替先は独立に検査してから有効にし、再実行と比較を可能にする。使用中の資産の削除は参照の解放と同期する。モデル、資料、結果、同意記録はそれぞれの保持規則に従って管理する。

## 8. 依存ライセンスと配布審査

### 8.1 採用基準

**製品が選択して組み込むコードは、許諾型（`permissive`）またはパブリックドメイン（`public-domain`）の条件を採用可能とし、GPL・AGPL・LGPL系（`gpl-family`）および商用許諾・有償コンポーネント（`commercial-paid`）は採用しない。** 著作権表示、ライセンス文、必要なNOTICEを配布物に含め、利用者が参照できるようにする。

`dependency_policy.json`は固定の許諾名リストではなく、この分類規則を定義する。分類はSPDX識別子や名称だけで決めず、上流の許諾全文、例外条項、適用対象の根拠から行う。選択した各条項の分類、出典、内容ダイジェスト、通知、再配布範囲を記録し、不明な分類は不適合とする。選択したファイル、リンク、機能、再配布単位まで評価する。[S14]

SPDX式は少なくとも一つの完全なOR分岐を選択でき、その分岐内のすべてのAND条項が採用可能であることを要求する。例外付き条項も全体として分類する。たとえばMIT OR GPLではMIT分岐を選べるが、MIT AND GPLは不適合となる。検証器のSPDX・独自条項の分類マップは規則を試す合成テストデータであり、製品依存の全一覧や実物の許諾根拠ではない。

この規則と合成テストだけでは、SQLCipherおよびネイティブ依存の推移的閉包の審査や、利用者が参照できる通知の実装は完了しない。これらは実際の依存構成・配布物を対象に別途検証する。

### 8.2 審査の範囲

| 区分 | 審査方法 |
|---|---|
| アプリコードと組込みライブラリ | 直接・推移的依存、静的・動的リンク、生成コードの許諾と由来 |
| プラグイン・補助プロセス | 配布・呼出し・データ交換・組合せの実態 |
| 実行時ロード | 検出されたファイル、検索経路、選択条件、依存閉包 |
| UI資産・フォント・辞書 | 表示、改変、埋込み、再配布に適用される条件 |
| 文書・映像処理 | パーサー、デコーダー、エンコーダー、特許・地域条件 |
| OSの基盤ランタイム | 提供元、動的リンク条件、再配布の有無、適用する根拠 |
| 外部OSサービス | 公開API・プロトコルの条件、製品に含む接続コード |
| ビルド・検査ツール | ツール自体の扱いと生成物へ含まれるコードの条件 |
| モデル | 利用者の導入領域における個別の利用条件 |

OSの基盤ランタイムはアプリ独自の機能ライブラリと区分し、対象ごとの根拠を記録する。配布やリンクの義務は実際の構成で確認する。動的ロードや別プロセス化は技術的境界であり、許諾評価は結合・配布の実態に基づく。[S14]

### 8.3 自動化

ビルド時にソフトウェア部品表を生成し、採用条件、選択した許諾、出典、著作権表示、ファイル内容、再配布範囲を照合する。各OSの配布成果物と実行時ロードの観測結果を検査する。配布ゲートは、許諾根拠、通知、モデル資産の別管理、依存の説明が揃った構成を通過条件とする。

配布候補の選定と法的適合の判断は担当を明確にし、判断の根拠を保持する。

### 9.2 位置と時間

テキストの保存はUTF-8を基本にし、外部契約で用いるオフセットの単位を明示する。UIの書記素位置、内部文字列の位置、元資料の位置は対応表で接続する。

画像は元画像の座標と変換行列、文書は章・ページ・要素、音声・映像は共通タイムラインとサンプル・トラック情報を保持する。原文と訳文の対応は区間の統合・分割も表現できるようにする。

### 9.3 訂正とイベント整合性

各処理に実行IDを割り当て、イベントはジョブ、実行ID、単調増加の順序、入力スナップショットを持つ。現在の処理と入力に一致するイベントを適用する。原文の訂正時は新たなスナップショットを作り、対象訳文を再確認状態へ移す。

部分結果は置換可能な表示データ、確定結果は記録対象として扱う。終端イベントは一回発行し、保存と表示の双方で冪等に適用する。

### 9.4 暗号化

保存を選んだ資料と結果は暗号化ストアへ置く。DBにはSQLCipherのコミュニティ配布を候補とし、採用するソース、暗号プロバイダー、通知条件を依存審査へ含める。[S15] 大きなデータは認証付きストリーム暗号のblobとして管理する。[S16]

鍵は利用環境の保護ストアへ格納する。利用可能な保護機能に応じて、審査済みのプロファイルでパスフレーズからの鍵導出と組み合わせる。検索インデックス、トランザクションログ、一時ファイル、サムネイルまで保存方針を揃える。

一時作業はメモリ内ストアを使い、利用者が保存を選んだ時だけ永続ストアを初期化する。長時間作業の復旧性と一時利用の保持期間は画面上で選択できる。鍵とストアは暗号化ストア内の認証対象メタデータで識別子・形式・暗号プロファイルを結び付ける。新規鍵の生成は鍵とストアの双方が不在と確認できる場合に限る。既存データに対する鍵の欠落、読出し失敗、不一致、破損、または初期化結果の不確定は復旧が必要な状態とし、書込みを止める。自動再生成、上書き、平文への切替、破損データの削除による初期化を行わない。中断・不確定な操作は既存状態を再読込して照合し、鍵とストアの再開可能性を確認するまで保存完了を表示しない。

各実行環境の保護範囲、ロック時の挙動、再インストール・プロファイル喪失時の可搬性は、実装・実行時利用可能・実機検証済みを区別して記録する。保護機能が未実装または未検証の環境では永続化を利用不可とし、メモリ内作業と未保存の表示を維持する。OS保護鍵の利用をハードウェア隔離や別端末への移行と同一視しない。

### 9.5 互換性と復元

保存形式は、必要な構造と能力の集合で適合を確認する。データ変換は、入力構造の照合、回復用コピー、トランザクション、変換後の照合を経て適用する。既知の変換経路へ解決できたデータを読み書きする。

バックアップには資料・結果・設定・モデルの参照情報を収める。モデル資産は利用者の導入手続で再取得・再選択できる。自動バックアップ、外部への転送、鍵の預託は既定で無効とし、保存先・保持・自動化は設定と利用者の明示的な選択に従う。

端末固有の保護鍵はポータブルバックアップへコピーしない。可搬バックアップは利用者が別途設定・保持する回復パスフレーズから、審査済みの鍵導出関数（KDF）と暗号プロファイルを用いて暗号化する。回復パスフレーズ、形式、KDFと資源上限は依存審査後に選び、プロファイルが無い間は可搬バックアップを利用不可とする。バックアップには版と必要能力を含む認証付きマニフェストを持たせ、秘密情報を含む内容は暗号化領域に収める。ローカルストアを解錠できる利用者は新しい回復パスフレーズで別のバックアップを作成できるが、旧バックアップは旧パスフレーズでのみ復元できる。回復パスフレーズと端末鍵の双方を失った場合、内容は復元不能であり、サービスによる鍵回復を約束しない。この制約は最初の保存とバックアップ作成前に説明する。

復元は未信頼の入力として形式・能力・資源上限・認証を検証し、既存ストアと分離した領域で暗号化して読戻し確認後に適用する。失敗や中断時は既存ストアを変更しない。復元先では新しい端末保護鍵を確立し、旧端末の鍵ファイルを移植しない。保存された許諾や権限記録は現在のOS権限・同意を代替しない。モデル資産の欠落や許諾不一致は依存処理を停止するが、適合する資料・訳文の復元を妨げない。

設定で変更できる保持方針の既定値は「利用者が削除するまで保持」とし、保存時に資料ごとの期間も選べる。期間を選んだ場合は期限到来後、Kotoha内で内容を表示・再利用できない状態にし、アプリが実行できる最初の保守機会に未参照のアプリ管理データを削除する。関連する鍵ラッパーは、他の有効な処理・ストアから必要とされない場合だけ削除する。OSがアプリを停止している間の即時消去や媒体上の安全消去は保証しない。アプリ管理バックアップにも設定された保持方針を適用し、利用者が書き出した外部コピーは利用者の管理下に置く。

利用者が明示的に削除を選んだ場合も期限到来時も、復旧や有効な処理から参照される間だけ削除を保留し、その状態を説明する。参照が解消した最初の保守機会に、選択された削除・保持方針に従って除去する。一時ファイルは作成した処理が所有し、成否と復旧要否を確認して不要となった後に除去する。論理削除は記憶媒体上の物理消去、OSバックアップ、スナップショット、書き出し済みバックアップの消去を保証せず、安全消去を約束しない。新規開始は復旧とは別の明示的な破壊操作として確認する。

## 10. 実行契約とライフサイクル

### 10.1 API

公開境界は固定幅整数、サイズ付き構造体、UTF-8の長さ付きバッファ、不透明ハンドルで定義する。能力照会で必要な契約・入力型・出力型を確認してから、ロードと処理へ進む。

ヘッダーは`specs/kotoha_api.h`に定義する。既存契約の意味を保ち、追加能力は名前付き能力と追加の操作契約として導入する。構造体は宣言サイズで読み取る範囲を決め、必要なフィールドと能力の充足を確認する。

### 10.2 所有権と並行実行

入力は呼出し中の借用と、非同期処理用の所有データを分ける。非同期処理へ渡す内容は呼出し終了までにコピーまたは管理された保持へ移す。出力は呼出元が確保したバッファへ返し、必要な容量を通知する。

エンジンコンテキストは所有する実行キューで直列化する。取消は協調的な要求として扱い、終端と資源利用の終了を確認して解放する。音声の入出力コールバックは固定容量のバッファ操作を担当し、推論・保存は専用キューで行う。

### 10.3 状態

モデルは候補、同意待ち、取得中、検査中、導入済み、ロード中、利用可能、解放中、削除待ちを持つ。ジョブは準備、待機、実行、一時停止、取消要求、成功、取消、失敗を持つ。終端は結果と復旧情報を確定する。

エラーは原因分類、再試行可否、影響する成果、必要な操作を持つ。利用者が扱える説明と、開発者が検査する診断情報を分ける。

## 11. 翻訳処理

入力確認、言語と区間の整理、構造の保護、用語・文脈の選択、実行予算の計算、推論、構造復元、意味上の確認支援、結果記録で構成する。

長文は論理的なまとまりを保って分割し、前後の文脈、見出し、表の項目、用語を計算予算内で渡す。入力、指示、文脈、用語、出力予約の合計をトークナイザーで評価する。処理が分割された場合は対応する原文範囲を結果へ添える。

特殊トークンやプロンプト構造はアダプターが生成し、利用者の原文は内容として区別する。出力はまず型付きのテキスト・構造データとして検査し、表示・保存へ渡す。

数値、単位、固有表現、参照、タグ、プレースホルダー等は保持・変換の方針に従って確認する。適用できる文体や用語指定は能力として表示する。逆翻訳・比較は理解の補助として、品質評価の根拠と区別して提供する。

生成キャッシュは原文、言語、文脈、用語、モデル内容、適用契約、生成設定の組で識別する。利用者の編集と承認済み翻訳メモリは生成キャッシュから独立させる。

## 12. 視覚・文書・構造化資料

### 12.1 視覚処理

カメラ・画像・画面入力は、向きと座標を正規化し、領域検出、追跡、認識、安定化、翻訳、表示へ流す。表示用映像と認識用の更新頻度を独立させる。追跡中の領域と内容が一致する結果を描画する。

重畳、吹出し、原文併記、訳文一覧、フリーズを用意する。文字列の修正は原画像の位置と紐づけ、変更した区間を再翻訳する。

### 12.2 資料の中間表現

文書は資料、章、ブロック、インライン要素の中間表現へ変換する。読順、スタイル、表、見出し、脚注、コメント、非表示要素、対象選択を保持する。認識で得た文字も同じ中間表現へ接続する。

| 資料 | 取込み・保持の方針 | 出力 |
|---|---|---|
| TXT・Markdown | 文字コード、段落、構文、コード領域 | テキスト、対照表示、対応形式 |
| HTML・Web | 本文、見出し、表、リンクと出典 | 読解用表示、対照HTML |
| CSV・TSV・JSON・XML | 指定値、列、キー、型、構造、エスケープ | 構造を保持した対応形式 |
| PDF | 文字抽出・OCR、ページ、読順、図表との対応 | 原資料対照、注記、適合する再構成 |
| 電子書籍 | 利用権限のある本文、目次、章、しおり | 対照読解、対応する書出し |
| DOCX | 本文、見出し、表、脚注等 | 対象要素を変換した文書 |
| PPTX | テキスト、ノート、位置、関連構造 | 配置調整・あふれ確認付きスライド |
| XLSX | 選択した文字列、型、数式、参照 | 指定範囲を変換したブック |
| 字幕 | 時間、区間、話者、表示属性 | 編集字幕、対照字幕 |

形式ごとに、扱う要素、保持する要素、要確認箇所、出力経路を能力情報として提示する。文字幅や配置の変化は再レイアウトと検査で扱う。

### 12.3 大容量処理

解析、認識、翻訳、整形を段階的に記録し、ページ・ブロック・区間単位で読み込む。表示中の対象を優先する。ジョブの再開には元資料と処理条件の一致を確認する。

一括処理は資料ごとに状態と成果を持つ。利用可能な部分成果、要確認箇所、再処理範囲を一覧で提示する。

## 13. 音声・映像

### 13.1 取得と時間管理

入力デバイス、チャネル、サンプルレート、時間基準を記録し、処理能力が要求する形式へ変換する。元の時間と認識・翻訳区間の対応を保つ。マイク、取得可能な再生音声、録音ファイル、映像の音声トラックを共通の音声契約へ接続する。

### 13.2 逐次処理

発話検出、認識の部分結果、安定区間、訳文、必要な音声出力を段階的に処理する。区切りは音響、言語、文脈、用途に合わせて調整する。直接音声翻訳などの複合経路も、原文確認や時間情報の要求を満たす構成として選択できる。

処理待ち時間、入力時刻からの遅れ、認識・翻訳待ち量を測る。待ち量が増加する場合は更新頻度・計算配分・処理経路を調整し、利用者へ状態を示す。保持予算に応じた一時停止と、保存許可のある入力からの再処理を提供する。

### 13.3 映像と字幕

映像はコンテナ、コーデック、音声・字幕トラック、時間軸を検査する。対応するOS機能または監査済み処理部品でデコードする。字幕は映像内、別ファイル、認識結果から選択できる。

字幕生成、編集、読みやすい分割、時間調整、原文・訳文の切替を提供する。ファイル出力、同期再生、映像への描画合成はそれぞれの出力能力として選ぶ。使用するコーデックの権利条件も依存審査へ含める。

### 13.4 合成と音声経路

読み上げは言語、音声、速度、出力先、割込み方針を持つ。出力音声の区間を入力処理へ通知し、エコー制御、入力選択、字幕優先を組み合わせる。出力先切断時は状態と再開方法を表示する。

OS側の音声を使う場合は、導入状態とローカル実行の適合を確認する。アプリ側の合成には利用者が導入した音声モデルを使用する。

## 14. 会話と話者

話者区間の推定、登録した声との照合、言語推定、音源分離、席の指定は個別の能力として扱う。処理結果には根拠と未確定状態を持たせる。

声の登録は目的、保持期間、利用範囲への同意を得て行う。必要な音響品質が得られた段階で特徴を登録し、保持方針に従って元音声を管理する。照合は会話内の表示振分けを目的とする。

話者の決定は利用者の明示指定を優先し、次に適合する照合結果を用いる。根拠が十分な区間だけ参加者へ割り当て、未割当の区間はその状態を表示する。訂正は関連する表示先・履歴・訳文へ反映する。

各参加者が読む言語に対して字幕を生成する。参加者ごとの表示方向、文字サイズ、原文併記、フォーカスを設定できる。表示人数と同時認識能力は別の資源指標として扱う。

重なった発話は重複区間として記録し、利用可能な分離・再認識・手修正へつなぐ。評価は短い発話、類似する声、距離、騒音、言語の切替、重なり、未登録話者を区分して行う。

## 15. モード定義と処理グラフ

モード定義は登録済みの処理能力を参照するデータとする。ノードは入出力ポート、必須能力、キュー方針、権限、資源見積りを持つ。定義追加は入出力・表示の組み合わせ、実装追加はアプリの配布工程で扱う。

処理グラフは一回のデータ伝播について有向非巡回として検査する。連続ストリーム、反復、利用者による再翻訳は実行管理のイベントとして繰り返す。分岐、結合、複数訳先、処理スキップを型付き契約で表す。

`mode_recipe.schema.json`の構造検査に加え、ノードの一意性、接続、型、権限、到達可能性、必須能力を検査する。グラフは全体の目的に必要な出力まで到達するものを実行計画へ変換する。

## 16. 資源・応答性・電力

UI、取得、認識、翻訳、合成、解析、保存の各処理へ共通予算を配分する。予算はメモリ、アクセラレーター領域、スレッド、待ちキュー、I/O、期限を含む。

モデルは必要な作業に合わせて読み込み、連続利用の見込みと資源状態に応じて保持する。解放は再ロード費用と比較して決める。キャッシュとメモリマッピングは、コピー量とピーク使用量を測定して適用する。

リアルタイムの取得は計算と分離し、期限付きの認識・翻訳、利用者の明示操作、表示中の資料、まとめ処理へ優先度を配分する。待機時間も加味して処理機会を調整する。

性能設定は応答性、品質、電力の優先順位を表す。モデル変更や処理経路の変更に伴う品質差を提示し、利用者の選択範囲内で適応する。

### 評価プロファイル

機種名に代えて、利用可能な演算能力、メモリ予算、アクセラレーター、入出力、熱状態、電源条件で試験構成を記述する。対応アーキテクチャやOS機能は実装・配布環境の能力表に記録する。

| 指標 | 測定と受入の決め方 |
|---|---|
| 操作応答・フレーム時間 | 計算中を含む分布を測定し、操作種別の時間予算へ適合させる |
| 起動 | 操作可能になるまでとモデル準備までを別測定 |
| 遅延 | 取得、認識確定、訳文開始、訳文確定、出力の各区間を測定 |
| 継続処理 | 入力に対する処理待ち量の傾向と熱安定後の性能を評価 |
| メモリ | UI、重み、作業領域、キャッシュ、GPU、IPCの合計とピーク |
| 容量 | 実行コード・UI資産・利用者導入モデルを別計上 |
| 電力 | 同条件の対照との差分、作業単位のエネルギー、継続負荷 |
| 取消 | 操作反映と安全な資源解放までを別測定 |
| 復旧 | 確定済み成果と再処理量、保存方針との一致 |

試験プロファイルは作業量、言語経路、文字体系、モデル内容、入力品質、熱・電源条件、時間予算を持つ。具体的な閾値は用途別の評価設計で定め、その条件と結果を公開できる形で保存する。

## 17. セキュリティとC++

### 17.1 安全性の契約

C++ではRAIIと所有権型、長さ付きデータ、検査済み演算、資源上限を基本にする。借用範囲と寿命をレビュー可能な形で示し、コンテキストごとの実行順序を固定する。外部境界は例外を契約エラーへ変換する。[S17]

文書、画像、音声、モデル、マニフェストは検査対象の入力として扱う。寸法、展開量、階層、要素数、メタデータ、処理時間を資源予算と照合する。大きな正当データは分割・逐次処理へ導く。

解析内容はデータとして処理する。実行権限はアプリが配布・検査する登録済み処理へ与える。モデルの特殊トークンや文書の能動要素は、内容と制御の境界を通して扱う。

### 17.2 隔離と復旧

環境が提供するプロセス・権限分離を活用し、処理workerへ必要な読取専用資産と出力領域を渡す。IPCは相手、メッセージ長、資源、所有権を検証する。同一プロセス内の処理は、監査・入力検査・実行順序・資源上限を中心に保護する。

障害復旧は確定済みの保存点と再実行計画で行う。隔離の強度と適用範囲をOS能力として記録する。

### 17.3 検査

静的解析、コンパイラ警告、メモリ・未定義動作・競合の検査、ファジング、取消と解放の競合試験を組み合わせる。[S18] モデル解析、アーカイブ展開、画像寸法、文字列境界、イベント順序、資源枯渇を重点対象とする。

依存の由来、既知の脆弱性、配布署名、ロード時の内容確認を供給網の検査へ含める。

## 18. プライバシーと通信

認識、解析、翻訳、話者処理、合成は利用端末の処理領域で実行する。処理用workerに与える権限は、必要な入力と出力に対応させる。

通信は取得・明示的な転送を担当する部品へ集約し、目的、接続先、対象データ、期限、利用者の許可を持つ操作として実施する。通信停止設定ではローカルファイルの取込みと端末内処理を利用できる。

アプリが管理するデータの経路と、外部のファイル提供者・入力手段・OSサービスが管理する経路を区別して表示する。通信試験はアプリ本体、同梱部品、選択したOS連携の範囲を明示して行う。

現在の手入力欄では、Androidの入力方法に対して入力履歴やユーザー辞書を個人学習へ反映しないよう要求し、既定は無効にする。利用者は現在のアプリセッション中のみ有効化でき、設定変更は次にテキスト欄へフォーカスしたときに反映する。この要求は入力方法による処理・保持を保証しない。iOSには同等のFlutterフラグがなく、他のOSもKotohaから入力方法の学習を制御しないため、利用者へ入力方法側のプライバシー設定を案内する。

カメラ、マイク、画面、ファイルの権限は用途と期間に対応させる。利用中の取得状態、保存範囲、参加者の同意、停止方法を表示する。生の音声・映像、話者特徴、原文・訳文には個別の保持方針を適用する。

診断は処理種別、状態、資源、時間、原因分類を中心とする。利用者が内容を確認してから、選択した診断情報を出力できる。

## 19. OS連携と自動化

OSが提供する共有、ファイル選択、カメラ、音声、画面取得、鍵保護、背景処理を能力として公開する。実行経路は利用可能な権限とライフサイクルに合わせて選ぶ。

共有拡張とブラウザ連携は、利用者が選んだ内容と権限を作業キューへ渡す。拡張と本体の寿命を分け、暗号化された受渡し領域と再開操作を用意する。

フォルダー監視は対象、再帰、除外、ファイル安定条件、出力先、キュー予算を設定する。CLIはGUIと同じ能力解決、モデル管理、実行契約、許諾状態を利用する。

```text
kotoha translate --source-language <tag> --target-language <tag> --stdin
kotoha document --input <path> --output <path>
kotoha subtitle --input <path> --target-language <tag> --output <path>
kotoha models list
kotoha models import --manifest <path>
kotoha capabilities --json
```

標準出力は成果、標準エラーは進捗・診断に使う。終了コードは成功、入力、能力、許諾、資源、取消、処理障害を区別する。自動化からの同意は、確認対象の許諾内容と適用範囲を明示して記録する。

## 20. 配布、更新、互換性

配布物はOSとアーキテクチャごとに再現可能な手順で生成し、署名、依存情報、通知、利用可能な能力を添える。アプリの実行コードとモデル資産を別の管理経路で扱う。Appleの配布条件には実行コードの取得に関する規定があり、この区分を配布審査でも確認する。[S19]

互換性は必要な能力、構造、操作契約で照合する。アプリの更新はコードと既存データの適合を確認し、回復手段を確保して適用する。モデルの切替は同意・内容・能力・進行中ジョブへの影響を確認して行う。

依存部品は内容と取得元を固定して再現性を持たせ、変更時に関連する機能・品質・許諾・安全性を再検査する。プラットフォームが配布管理に要求するメタデータは配布基盤が管理する。

## 21. 品質と受入

### 21.1 機能受入

各機能について、通常利用、編集、取消、権限変更、導入状態、資源不足、入力の問題、処理中断、再開、出力、アクセシビリティを確認する。適用条件は能力表と一致させる。

### 21.2 多言語品質

評価は言語方向、文字体系、領域、文章長、音響・画像品質、文体、混在言語で層別化する。評価対象は利用可能な能力と利用状況に基づいて選び、各言語経路へ同じ評価手続きを適用する。

翻訳は意味保持、抜け・追加、重大な意味変化、数値・固有表現、流暢さを測る。音声・文字認識は適切な区間・語・文字単位を選び、話者処理は誤割当と判定できた割合を併記する。測定条件、標本、評価者の適性、指標、信頼区間を記録する。

### 21.3 構造・安全・復旧

入力と出力の構造、原資料の保持、編集の優先、同意の範囲、イベントの整合、暗号化、通信、資源解放を検査する。停止・強制終了・容量変化・権限変更を各処理段階へ注入して復旧を確認する。

### 21.4 配布受入

機能と能力表、UI資産、プラットフォーム統合、モデルの導入・削除、依存許諾、通知、署名、保存形式の適合、サポート情報を配布物単位で照合する。基盤として採用するLinuxホストも同じ機能・文字入力・アクセシビリティ基準で受け入れる。
