# Translation-route audit

## Current product state

`lib/main.dart` implements a manual text workspace: users can enter text, import supported text documents, edit separate translation fields, and copy or export field contents. The UI labels translation entry as manual and explicitly says that automatic translation is not provided. This describes the current route; it does not claim that the app processes no material.

The iOS deployment target is iOS 15. No translation engine is currently adopted. The design target and current route are distinct (`design/kotoha_design.md` §§7.1, 11, 18 and 21).

## Apple Translation candidate (installed-only initializer; iOS 26+)

Apple documents the `TranslationSession` class and `LanguageAvailability` on iOS/iPadOS 18.0+, with translation performed on-device. This class-level availability does not make every initializer available on that OS. Apple may collect API usage and performance metrics including the app bundle ID and language pair, but not translation content. This is an iOS-specific candidate, not a cross-platform route.

`LanguageAvailability.status(from:to:)` and its `.installed` state are available on iOS/iPadOS 18.0+ and report language-pair installation status. A static list or a guess does not establish which pairs are supported. A status check does not configure a session to forbid downloads.

The direct `TranslationSession.init(installedSource:target:)` initializer is introduced in iOS/iPadOS 26.0, not iOS 18; it requires the languages to be installed and throws if they are absent. SwiftUI `.translationTask` is available earlier but can always request system-authorized downloads when assets are missing. The documented `canRequestDownloads` property is also iOS/iPadOS 26.0+, so the reviewed API material does not establish an iOS 18 session that guarantees no download request. The iOS 26 initializer is not an iOS 18 route. An iOS 18 installed-only route remains out of scope until a distinct documented mechanism is established.

### Smallest candidate flow

- One explicit action translates one text field for one selected source/target pair.
- The action is available only when dynamic availability says the pair is supported and already installed.
- The source stays unchanged; the result goes into a separate editable field.
- This slice covers only text, not documents, images, audio, video, or other modalities.

### Evidence and release gates not met

- Physical iOS/iPadOS 26+ runtime test on an actually available pair, including translation quality. No physical test device/session is currently available; no distinct installed-only iOS 18 route is established.
- Offline behavior, error handling and cancellation.
- An iOS 26 installed-only route requires testing no-download error behavior when assets are absent. An earlier `.translationTask` route requires testing the system download-consent flow; its documented session can request downloads and is not equivalent to an installed-only initializer.
- Disclosure of relevant system metrics and review of the privacy policy and telemetry disclosures.
- The public API material reviewed exposes neither model identity/version, provenance, nor model license/redistribution terms. Kotoha would not package OS assets; the API material does not establish that the model is open or that Kotoha may redistribute it.

No route is evidence-complete now. Automatic translation and all engine adoption remain disabled.

## Browser built-in translation API candidate (desktop only)

MDN documents experimental `Translator` and `LanguageDetector` web APIs that translate text and detect language through a browser-managed internal AI model, which may differ between browsers, instead of an app-bundled engine. Creation requires a secure context and recent user activation; access is gated by the `Permissions-Policy` `translator`/`language-detector` directives; pending `create()`/`detect()`/`translate()` operations can be cancelled with an `AbortController`; and `destroy()` releases the model's resources. These are documented interface capabilities, not a Kotoha runtime observation.

MDN browser-compat data records `Translator` and each reviewed member (`availability()`, `create()`, `destroy()`, `inputQuota`, `measureInputUsage()`) as Chrome 138 and Edge 148, with `chrome_android: false`, `webview_android: "mirror"` (so Android WebView is unsupported), Firefox/Safari/Deno/Node.js `false`, status experimental, and the note that availability "may be subject to geographical restrictions." A search excerpt of Chrome's developer documentation states these APIs "work in Chrome on desktop" and "don't work on mobile devices." The excerpt is not independently verified here.

Consequence for this Android-first product: the browser-managed on-device translation API, a browser route that would avoid an app-bundled engine and model weights, is unavailable on Android Chrome and Android WebView. A browser path on the target platform would still require the separately inspected WASM/worker engine route, whose real inference, offline reload, cancellation cleanup, model consent, resource and mobile evidence remain unproven. Search excerpts, not independently verified here, indicate that even that route's acceleration prerequisites are constrained on mobile: WebGPU has limited availability (Android Chrome 121+ only on Android 12+ with Qualcomm/ARM GPUs), and multithreaded WASM needs cross-origin isolation (COOP/COEP) for `SharedArrayBuffer`.

The built-in API also exposes no documented model identity/version, provenance or redistribution terms, and depends on browser/OS-managed language-pack downloads whose consent and offline lifecycle are not established here. No browser support claim, model-rights conclusion or adoption follows. Rights, offline, consent and adoption gates stay unresolved; automatic translation and engine adoption remain disabled.

Host-maintenance comparison (planning only, no host implementation or adoption): a Flutter Web/WASM host would reuse the existing Dart UI source, workspace state machine and test suite but would need a new browser engine adapter, a new model-acquisition/offline lifecycle, browser accessibility verification and separate web distribution checks. A DOM SPA/PWA would share none of the UI, state or widget tests and would add a second language and UI stack; it would still need engine integration, model lifecycle, accessibility and distribution work of its own. Relative to the current Android-first native path, both browser hosts shift engine and model-offline ownership rather than removing it, and neither is shown here to reduce total maintenance. Unknowns (unstated, not assumed): Web/WASM inference output parity with native, browser model persistence and consent behavior, screen-reader/keyboard parity, and the real cost of maintaining a second host were not measured or implemented. This comparison records shared versus new ownership only; it opens no browser, engine or adoption gate.

## PLaMo model license terms (candidate model rights)

The candidate model family discussed in the browser and native probes, PLaMo 3 Translate, is licensed separately from any engine runtime. PFN's own [`plamo-translate-cli` README](https://github.com/pfnet/plamo-translate-cli/blob/main/README.md) states that the CLI source is Apache-2.0, while the models it downloads — `pfnet/plamo-3-translate-2b`, its GGUF, the `0.8b-GGUF` draft and the PLaMo 2 Translate models — are distributed under the PLaMo Community License, not Apache-2.0.

That first-party README summarizes the license terms as: personal and non-commercial use, including academic use, is free and needs no registration; commercial use is free when the revenue or sales of the user or its affiliates in the most recent fiscal year were 1 billion yen or less, after registering through PFN's commercial-use form, with use inside an organization counted as commercial use, and a separate PFN agreement required above that threshold; published translations must be indicated as model output (Article 5); and providing the models or their output to others requires a copy of the license for recipients, "Built with PLaMo" in related websites/interfaces/documentation, and "PLaMo" in the names of derived models (Article 4). The README expressly states that the license text is authoritative and its summary is not. The authoritative license host (`plamo.preferredai.jp`) and the model-card license were refused by this environment's destination decider, so the exact binding text was not retrieved here; search excerpts of the agreement (not independently verified here) corroborate the non-exclusive, worldwide, non-transferable, royalty-free grant, the registration and revenue threshold, and the redistribution/attribution obligations, but are not the authoritative text.

Attempts to bind the authoritative full text failed within this environment's fetch policy: `plamo.preferredai.jp`, `huggingface.co` and `imoz.jp` were each refused by the destination decider, and PFN's own `plamo-translate-cli` git tree contains only the Apache-2.0 CLI `LICENSE` and the summary README, no vendored copy of the Community License (tree root `82788925ce64b5ec15abb25a650ccf4616eff57a`; repository/author searches returned no vendored full-text mirror). Verbatim Articles 1–5 text appears only in search excerpts, which are not independently verified or bound to exact source bytes. Those excerpts also report that the agreement is a moving document: established 2025-02-25 and revised 2026-11-09 (Hugging Face commit `8b797b290907c84403877cb9d03150929f10b467`), with PFN able to modify it after notice and terminate on breach. Any future binding must therefore pin an exact revision, not just a URL. No authoritative full-text SHA-256 is established here.

These documented terms do not close the rights gate. No evidence establishes that Kotoha or its operator qualifies for the no-registration or <=1-billion-yen free commercial tier, or has completed PFN registration. Adopting the model would carry the Article 4 attribution/naming and Article 5 output-labeling obligations into product notices and UI; no such notice is added here, no weights were downloaded or bundled, and no engine is adopted. The authoritative license text, the exact language pair and conversion/GGUF route, translation quality, and the platform runtime evidence remain to be established before any rights or adoption decision.

## Hy-MT2-1.8B candidate model provenance (evidence only, no adoption)

A separate candidate, `tencent/Hy-MT2-1.8B`, closes two gaps earlier model-license reviews left open: the exact revision and the LICENSE/NOTICE bytes. The evidence was fetched externally and byte-hashed at fetch; this environment's destination decider refuses `huggingface.co`, so none of it was independently re-fetched here. The values below are registry-declared pins recorded for evaluation, not bytes verified against a local download.

- Base model `tencent/Hy-MT2-1.8B`: repository commit `9a341cd1b679d3efd23b46e847b01745a71ed792` (last modified 2026-05-26, not gated) is tagged `license:apache-2.0`, `ja`, `en` and 33 languages; paper arXiv:2605.22064; architecture `HunYuanDenseV1ForCausalLM`. The repository carries `LICENSE.txt` and no NOTICE file.
- LICENSE at that commit: `LICENSE.txt` SHA-256 `1af3c6dc0c697277cbb6b68720787c1caa43a79c5626bf9f19cd8c00de9c8cd4`, byte-identical to the `raw/main` fetch. It is the full Apache-2.0 text under the header "Copyright (C) 2026 Tencent. All rights reserved. Hy-MT2-1.8B is licensed under the Apache License, Version 2.0."
- Community-license warning resolved: a secondary report that Tencent's visible files still carried a "Tencent HY Community License" describes the pre-renewal state. Primary GitHub commit `c30b36c5` ("renew license", parent `fd271be`, 2026-05-26) changed only `LICENSE.txt` (+208/-80) to Apache-2.0. The exact pinned artifact is Apache-2.0; this is why the exact artifact, not the headline tag, must be checked.
- GGUF artifact that would be imported: `tencent/Hy-MT2-1.8B-GGUF` commit `a0c709d9fac510f2c807aa3af52872340dc37a4a` (last modified 2026-09-08, not gated, `license:apache-2.0`, `base_model` `tencent/Hy-MT2-1.8B`). Registry-declared LFS SHA-256 and sizes: `Hy-MT2-1.8B-Q4_K_M.gguf` `dc5f44fcf1fa496ee7ad725982c0c8c553a4de00259b53af84c4b89fb0c06699`, 1,133,080,448 bytes (~1.08 GiB); Q6_K prefix `d98fe604`, 1,474,785,120 bytes; Q8_0 prefix `5c3fe0b1`, 1,908,528,192 bytes. No NOTICE file.
- Runtime/footprint constraint: the official GGUF repository ships only Q4_K_M/Q6_K/Q8_0. The ~441 MB, 1.25-bit, 1.5x-speed claim belongs to a different repository, `tencent/Hy-MT2-1.8B-1.25Bit-GGUF` (commit `9df5c824`, `totalFileSize` 461,860,800 bytes), whose conversion depends on the STQ/AngelSlim kernel (llama.cpp PR #22836, still open as of 2026-11-18; follow-up PR #27377 describes it as an ARM-NEON STQ1_0 kernel that falls back to the scalar generic path on x86, so low-bit would not accelerate our macOS/Windows/Linux desktop targets even if merged). Third-party cards report that 1.25-bit needs STQ1_0 kernel dispatch with a broken NEON kernel and was tested through that PR. An independent Apache-2.0 Android arm64 GGUF/llama.cpp translation SDK (`localmt`) that SHA-256-verifies model packs lists "1.25bit mobile target: Waiting on stable upstream STQ1_0 / Sherry support" and its device smoke as still pending; Q4_K_M is its proven path. Even a dedicated project has not demonstrated the low-bit quant on device.

First host proof correctness requirement: a single hands-on third-party report (external-untrusted, one M1 Max/64 GB, Homebrew llama.cpp build 8990, ggml 0.10.1, 2026-05-26) found that a mainline Q4_K_M run only interpreted the translation instructions when the server applied the model's bundled chat template (that report used `llama-server --jinja`, with `<｜hy_User｜>` / `<｜hy_Assistant｜>` turns). Without it, the model runs in raw-completion mode and silently ignores the translation instructions; putting the instructions and source text in one user turn also led it to translate its own instruction headers, so instructions must be separated from source text via a system prompt or explicit delimiters. A proof that wires up Q4_K_M without template application can appear to work while invalidating the result. The future first host proof must therefore assert that the bundled template is applied and that instructions and source text are separated before any "Q4_K_M works" conclusion; llama.cpp mainline HunYuan dense support (PR #14878 merged 2025-08, `src/models/hunyuan-dense.cpp`, matching the pinned `hunyuan_v1_dense` config) makes that route architecture-feasible. The same report reads the paper's quantization evaluation as 2-bit and 1.25-bit losing instruction-following while 4-bit/FP8 preserve format and terminology, consistent with keeping Q4_K_M as the baseline.

Contract gap deferred, not filled now: `design/specs/model_manifest.schema.json` has `files[].role` in {weights, tokenizer, vocabulary, configuration, terms, auxiliary} and a free-form `executor.required_capabilities`, but no file role, capability or field to pin a chat/prompt template or require the adapter to apply it; `engine_event.schema.json` carries no prompt/template metadata either. No schema or file-role change is made here: no engine or adapter is adopted, adding a role would need coordinated changes in the schema and Dart's `_fileRoles`, and `--jinja` is a llama-server flag that a different adapter could legitimately bake in, so pinning a template artifact now would be speculative and could misrepresent other adapters. The contract decision is deferred to engine+adapter selection; until then the host proof asserts template application and instruction/source separation explicitly.

Boundary for these additions: one external-untrusted third-party report from one device and build in May 2026, not reproduced here; no pinned llama.cpp build, no local run, no device memory/latency or ja<->en quality measurement; architecture feasibility is from merged-PR/source records, not a locally verified build; the low-bit instruction-following reading is that report's, not our measurement. LFS hashes remain registry declarations. Adoption, bundling, engine, quality and distribution gates stay closed.

Decision effect for the first translation slice: the rights/provenance sub-gate for this one candidate can now be evaluated on pinned bytes rather than card metadata (base commit + LICENSE SHA-256 + GGUF commit + Q4_K_M LFS SHA-256). The declared Q4_K_M weight-file size is ~1.08 GiB (1,133,080,448 bytes) — a registry-declared file length, not a measured runtime memory footprint. The 1.25-bit variant's declared repository total is 461,860,800 bytes (~441 MB), also not a measured footprint, and is not proven without an unmerged kernel. Resident model pages, KV cache, scratch buffers and app memory remain first-proof measurements. The first host proof should therefore use Q4_K_M on a pinned mainline llama.cpp, with 1.25-bit/STQ kept as a blocked optimization, not a planning baseline. Declared LFS hashes must be checked against an actual local download before any adoption.

Evidence boundaries still open: all receipts are external HTML/JSON/plain text hashed at fetch and were not independently re-fetched here; LFS hashes are registry declarations, not locally verified bytes. Neither repository has a NOTICE file, so Apache-2.0 §4(a-c) license-copy, change-notice and retained-notice duties still apply. No ja<->en quality, target-device memory/latency or on-device smoke was measured; no Flutter plugin was vetted, no llama.cpp build pinned, and no consent/acquisition flow established. The `localmt` output claim is that project's, not a measurement here. Tokenizer/base/dataset license inventory and llama.cpp build provenance remain open. No weights were downloaded or bundled, no engine adopted, and the rights, adoption, bundling, quality and distribution gates all stay closed.

## Index-Translate-2B candidate (second Apache-2.0 family, evidence only, no adoption)

A second llama.cpp-native, permissively tagged candidate surfaced in configured feeds, retrieved 2026-11-18T13:14Z as external-untrusted primary model cards (GGUF receipt `7bb9ac0d1e02876612668e1a384efb98ac3e492dc4fa9048161fa8af682b8eb2`, base receipt `117c133e44d2f1e533cc32c62bdc5b8b0fd9bd4034ea48b21e4eca357ea07f94`). The cards describe Index-Translate (Bilibili Index team), base published 2026-09-30 and GGUF conversion 2026-10-03, based on Qwen3.5. They declare `apache-2.0` on both base and GGUF repositories, state the GGUF was converted with llama.cpp master (2026-10), offer a recommended ~1.31 GB Q4_K_M plus a quant ladder, and ship an mmproj for image translation. These are card declarations, not bytes verified or downloaded here.

Decision-relevant claim for the first slice: the card documents an `instTrans` constrained-translation prompt contract whose hard constraints are strict glossary/terminology enforcement and preservation of JSON/CSV/Markdown/code/placeholders, with soft constraints for tone/style and domain disambiguation — the F03/F04 needs the Hy-MT2 section does not currently establish. A second, independent model family therefore becomes a comparison candidate for glossary and structure/placeholder preservation, alongside ja<->en, when the first-slice model choice is actually evaluated. No evaluation was run here.

Generalized host-proof requirement: this family's card also requires `--jinja --chat-template-kwargs '{"enable_thinking":false}' --temp 0`, one user message with no system message, and stripping emitted `<think>` tags; its canonical format separates source (【源文】) from constraints (【约束要求】) so the model does not translate its own instructions. Together with the Hy-MT2 report, two independent families now require template application plus instruction/source separation: this is not a Hy-MT2 or llama-server one-off, and a thinking-mode disable/strip requirement is added. The host proof must assert these properties for whichever candidate is chosen; the deferred schema/contract decision in the Hy-MT2 section is unchanged.

Evidence boundaries: the repository tag is Apache-2.0, but LICENSE file bytes/hash were not verified here (contrast Hy-MT2's pinned LICENSE SHA `1af3c6dc`); Japanese is listed among 150 languages in the technical report rather than explicitly confirmed by the card (`README_ja.md` is UI documentation); benchmark comparisons against Hy-MT2-1.8B (e.g. FLORES COMET-22 0.8655 vs 0.8522, instTrans IFscore 0.7569 vs 0.4932, WMT26 Judge 60.26 vs 49.35, low-resource off-target 4.2% vs 54.2%) are the competing vendor's self-reports, validated on A100, not reproduced or measured by us. No ja<->en measurement, device test, pinned llama.cpp build, redistribution/notice decision or audio-family evidence was established. Recording this candidate opens no gate: rights, adoption, bundling, engine, quality and distribution remain closed, with no download, pin or engine enablement.
