# Translation-route audit

## Current product state

`lib/main.dart` implements a manual text workspace: users can enter text, import supported text documents, edit separate translation fields, and copy or export individual field contents or the whole workspace, and restore a whole workspace from a v2 export document. The UI labels translation entry as manual and explicitly says that automatic translation is not provided. This describes the current route; it does not claim that the app processes no material.

The iOS deployment target is iOS 15. No translation engine is currently adopted. The design target and current route are distinct (`design/kotoha_design.md` §§7.1, 11, 18 and 21).

## Apple Translation candidate (installed-only initializer; iOS 26+)

Apple documents the `TranslationSession` class and `LanguageAvailability` on iOS/iPadOS 18.0+, with translation performed on-device. This class-level availability does not make every initializer available on that OS. Apple may collect API usage and performance metrics including the app bundle ID and language pair, but not translation content. This is an iOS-specific candidate, not a cross-platform route.

`LanguageAvailability.status(from:to:)` and its `.installed` state are available on iOS/iPadOS 18.0+ and report language-pair installation status. A static list or a guess does not establish which pairs are supported. A status check does not configure a session to forbid downloads.

The direct `TranslationSession.init(installedSource:target:)` initializer is introduced in iOS/iPadOS 26.0, not iOS 18; it requires the languages to be installed and throws if they are absent. SwiftUI `.translationTask` is available earlier but can always request system-authorized downloads when assets are missing. The documented `canRequestDownloads` property is also iOS/iPadOS 26.0+, so the reviewed API material does not establish an iOS 18 session that guarantees no download request. The iOS 26 initializer is not an iOS 18 route. An iOS 18 installed-only route remains out of scope until a distinct documented mechanism is established.

### Smallest candidate flow

- One explicit action translates one text field for one selected source/target pair.
- The action is available only when dynamic availability says the pair is supported and already installed.
- The source stays unchanged; the result goes into a separate editable field.
- This slice covers only text, not documents, images, audio, video, or other modalities.

### Evidence and release gates not met

- Physical iOS/iPadOS 26+ runtime test on an actually available pair, including translation quality. No physical test device/session is currently available; no distinct installed-only iOS 18 route is established.
- Offline behavior, error handling and cancellation.
- An iOS 26 installed-only route requires testing no-download error behavior when assets are absent. An earlier `.translationTask` route requires testing the system download-consent flow; its documented session can request downloads and is not equivalent to an installed-only initializer.
- Disclosure of relevant system metrics and review of the privacy policy and telemetry disclosures.
- The public API material reviewed exposes neither model identity/version, provenance, nor model license/redistribution terms. Kotoha would not package OS assets; the API material does not establish that the model is open or that Kotoha may redistribute it.

No route is evidence-complete now. Automatic translation and all engine adoption remain disabled.

## Browser built-in translation API candidate (desktop only)

MDN documents experimental `Translator` and `LanguageDetector` web APIs that translate text and detect language through a browser-managed internal AI model, which may differ between browsers, instead of an app-bundled engine. Creation requires a secure context and recent user activation; access is gated by the `Permissions-Policy` `translator`/`language-detector` directives; pending `create()`/`detect()`/`translate()` operations can be cancelled with an `AbortController`; and `destroy()` releases the model's resources. These are documented interface capabilities, not a Kotoha runtime observation.

MDN browser-compat data records `Translator` and each reviewed member (`availability()`, `create()`, `destroy()`, `inputQuota`, `measureInputUsage()`) as Chrome 138 and Edge 148, with `chrome_android: false`, `webview_android: "mirror"` (so Android WebView is unsupported), Firefox/Safari/Deno/Node.js `false`, status experimental, and the note that availability "may be subject to geographical restrictions." A search excerpt of Chrome's developer documentation states these APIs "work in Chrome on desktop" and "don't work on mobile devices." The excerpt is not independently verified here.

Consequence for this Android-first product: the browser-managed on-device translation API, a browser route that would avoid an app-bundled engine and model weights, is unavailable on Android Chrome and Android WebView. A browser path on the target platform would still require the separately inspected WASM/worker engine route, whose real inference, offline reload, cancellation cleanup, model consent, resource and mobile evidence remain unproven. Search excerpts, not independently verified here, indicate that even that route's acceleration prerequisites are constrained on mobile: WebGPU has limited availability (Android Chrome 121+ only on Android 12+ with Qualcomm/ARM GPUs), and multithreaded WASM needs cross-origin isolation (COOP/COEP) for `SharedArrayBuffer`.

The built-in API also exposes no documented model identity/version, provenance or redistribution terms, and depends on browser/OS-managed language-pack downloads whose consent and offline lifecycle are not established here. No browser support claim, model-rights conclusion or adoption follows. Rights, offline, consent and adoption gates stay unresolved; automatic translation and engine adoption remain disabled.

Host-maintenance comparison (planning only, no host implementation or adoption): a Flutter Web/WASM host would reuse the existing Dart UI source, workspace state machine and test suite but would need a new browser engine adapter, a new model-acquisition/offline lifecycle, browser accessibility verification and separate web distribution checks. A DOM SPA/PWA would share none of the UI, state or widget tests and would add a second language and UI stack; it would still need engine integration, model lifecycle, accessibility and distribution work of its own. Relative to the current Android-first native path, both browser hosts shift engine and model-offline ownership rather than removing it, and neither is shown here to reduce total maintenance. Unknowns (unstated, not assumed): Web/WASM inference output parity with native, browser model persistence and consent behavior, screen-reader/keyboard parity, and the real cost of maintaining a second host were not measured or implemented. This comparison records shared versus new ownership only; it opens no browser, engine or adoption gate.

## Android 16 KB page-size gate for future native dependencies (external-untrusted, no adoption)

A search role reported that Android 15 (API 35) supports 16 KB memory pages and that Google Play requires 16 KB support for apps with native libraries targeting API 35+, citing a primary Android Developers guide (fetch receipt prefix `ab2dd08f`, search receipts `aad0a1db` / `48eb1bcc`). The reported enforcement date differs between the current guide (2027-02-01) and an earlier Android blog (2025-11-01), so it must be re-checked at adoption time. The guide directs inspecting ELF LOAD-segment alignment (`>=0x4000`) in packaged `.so` files and testing on a 16 KB device; unaligned libraries can fail to install or load. A third-party article reports that Flutter >=3.38 defaults to NDK r28 (first NDK aligning native code for 16 KB by default) with AGP >=8.5.1 and build tools >=35.0.0; the pinned toolchain has since been confirmed from first-party source (below), while the project's API 35 emulator's page size is still not documented, so that CI run alone is not 16 KB evidence. A `fllama_cpp` changelog reportedly states its Android ggml CPU libraries are 16 KB-aligned; no equivalent public statement was found for the other candidate plugins (an access gap, not proof of misalignment).

The current first-party [Android Developers page-size guide](https://developer.android.com/guide/practices/page-sizes) was fetched directly with receipt `bc7fd882a8f0277b24e8a21f5fb8162068bd8d994497c5d1662d86b3d80b9d55`, SHA-256 `ff30e1a88fdfd0cf6fd160ba3646d52afa2a7ac445fd09d9e812c3950d91095e`. It specifies that every packaged shared object's ELF LOAD segments must have alignment at least `2**14` (checked with NDK `llvm-objdump -p ... | grep LOAD`, or APK Analyzer), that `zipalign -v -c -P 16 4 APK_NAME.apk` must verify, and that when a `GNU_RELRO` segment shares a writable LOAD with later writable data its end (`VirtAddr + MemSiz`) must be 16 KB aligned; a missing `GNU_RELRO` is also compliant. NDK r28 and higher align by default, while r27 and lower need `-Wl,-z,max-page-size=16384 -Wl,-z,common-page-size=16384`; prebuilt `.so` files must be rebuilt with the same settings, and code must use `sysconf(_SC_PAGESIZE)` rather than assuming 4 KB pages. These are first-party build/runtime criteria, not evidence about any candidate artifact here.

The toolchain side of the NDK question is now bound from first-party source. The project's `.metadata` pins Flutter revision `c197ca5199e9ee5661e865596c9c07294dfab51c` on the stable channel, and `.github/workflows/ci.yml` installs Flutter `3.47.9` in its Android and Flutter jobs. At both that revision and the `3.47.9` tag, `packages/flutter_tools/gradle/src/main/kotlin/FlutterExtension.kt` declares `val ndkVersion: String = "28.2.13676358"` (receipts `6e0581d7439ac16165960cb2cce7fc995bf868e59893a31b4bafb2c1b9458e59` and `64c5817bf10285b840af564f51b0bfeddab27cfda24f61f26c70db52ccfa530b`, both full-file SHA-256 `a8ca02d55798c200d766e245dae9df20565cb9d638d4887b51bf617abac938a1`). The project's `android/app/build.gradle.kts` sets `ndkVersion = flutter.ndkVersion` and `android/gradle.properties` has no override, so toolchain-built code uses NDK r28; adding `max-page-size`/`common-page-size` flags on the assumption of r27 would be wrong. This resolves only the toolchain-default question: prebuilt or vendored `.so` files must still be rebuilt/aligned and checked per artifact, packaging must still pass `zipalign -v -c -P 16 4 APK_NAME.apk`, and every packaged 64-bit library must still pass the per-`.so` LOAD and GNU_RELRO checks on a release artifact. The CI workflow's declared Flutter version and the absence of a local release build mean no packaged artifact is proven by this source evidence alone.

No AAB, `.so`, emulator or device run was inspected locally; the claims above remain external-untrusted until reproduced. The gate for any future engine, OCR or storage native is a release-like AAB-to-per-ABI APK check of every `.so` for LOAD and GNU_RELRO alignment plus `zipalign -P 16 4` and a 16 KB Android 15 emulator run of the real model-load path, recorded for the chosen library. NDK r28 defaults or a changelog's "16 KB aligned" claim do not satisfy this gate without the release artifact check. No dependency, library or model is adopted, downloaded or bundled by recording this gate.

### Offline first-party ELF preflight (evidence only, no adoption)

The documented first-party criteria are now executable locally against a built APK or AAB:

```sh
python3 tools/android_16kb.py PATH_TO_APK_OR_AAB
```

This stdlib-only tool opens the ZIP, checks every entry ending in `.so`, parses ELF64 little-endian headers and program headers in memory, prints one `PASS`/`FAIL` line per library with the entry path and numeric values, and exits 0 only when at least one `.so` was found and every `.so` passes. It requires every `PT_LOAD` to have `p_align >= 16384`; for `PT_GNU_RELRO` it requires the end (`p_vaddr + p_memsz`) to be 16 KB aligned only when the RELRO start lies in a writable `PT_LOAD` that has data beyond that end, and passes when RELRO is absent or no such writable LOAD contains it. Truncated, malformed or unsupported objects (including ELF32 and big-endian) and archives with no `.so` fail closed with explicit findings. AAB results are pre-upload evidence only; the release APK must still be checked. A passing report is not Android compliance, a release gate, or evidence of engine adoption; the tool has been exercised only with synthetic ELF fixtures, not a real artifact.

Gates this preflight does NOT cover: zipalign verification (`zipalign -v -c -P 16 4 APK_NAME.apk`), a 16 KB emulator/model-load proof, license closure, and quality checks all remain separate unmet gates.
